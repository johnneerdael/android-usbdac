# USB audio feedback implementation design

Baseline `b309a080be571677ec432e599e83333f970704f6` in `android-usbdac`. This design describes proposed changes to the MIT-licensed direct USB driver and the evidence needed to ship them.

## 1. Decision

Implement **implicit feedback first**. The driver already polls explicit feedback asynchronously and uses it to pace playback. The gap is asynchronous OUT playback with a compatible IN audio endpoint serving as the clock reference. Implement the reference's IN-first, bounded packet-pattern queue in the existing Rust USB worker. Use whole audio-frame counts as the queue unit, constrain pairing to the same audio function and sample cadence, and make feedback lock and failure observable to callers. Harden the existing explicit path in a second batch using the same stream health contract.

The direct driver will choose explicit feedback when a valid dedicated pipe exists. It will choose implicit feedback when it can prove a safe pairing and configure both endpoints. The existing `allowUnsynchronizedAsync` escape hatch remains opt-in and carries the existing bit-perfect blocker. Add a session-level feedback disable option for diagnosis, defaulting to feedback enabled. Keep policy and the transport in `usbdac-core` so apps can use the library without adopting the sample player or its UI.

Both mechanisms control the number of frames pulled into each OUT packet. They leave sample words, sample order, encoding, and user-requested conversion policy with the existing payload path. The reference model supplies the starting algorithms. USB-IF and Linux are independent checks of the protocol and compatibility behavior. The repository's MIT license and existing attribution apply to the new implementation.

Examples of errors a direct port would introduce:

- A 48 kHz high-speed report of 6 frames per microframe means **48 frames per OUT packet** when OUT `bInterval = 4`, whatever the feedback endpoint's poll interval.
- IN with two 3-byte channels and OUT with two 4-byte channels require 288 IN bytes to become 48 frames and then 384 OUT bytes. The reference's exact channel ratio leaves the length at 288 bytes.
- With an OUT capacity of 48 frames, a fractional rate of 48.05 frames per service eventually needs a 49-frame packet. The reference's floor-only capacity check admits it.
- Four bytes reserved for a feedback report are unrelated to the bytes per playback frame. A valid empty feedback response advances neither the accepted-report count nor the time of the last valid report.

## 4. Implicit feedback

### 4.1 Discovery and selection

Model each endpoint by configuration, AudioControl interface, AudioStreaming interface and alternate, direction, address, protocol, usage, sync type, interval and capacity. Carry `bTerminalLink`, format, channel count, subslot width and rate constraints for IN candidates. Keep malformed and missing links distinguishable from unlinked asynchronous endpoints. Represent the selected mode internally as one of nominal, explicit with its pipe, or implicit with its source plus pairing evidence.

Apply these rules in order to an otherwise viable OUT alternate.

1. For synchronous or adaptive OUT use nominal timing. For asynchronous OUT prefer a valid explicit pipe. Inspect the target's usage before admitting a nonzero `bSynchAddress`. The current linked-endpoint branch can accept an IN data endpoint as explicit. Route a linked marked data source through the implicit checks below. Report explicit ambiguity as a malformed pairing. A declaration that cannot be honored blocks admission unless a documented quirk supplies a replacement.
2. For automatic implicit pairing, require a UAC2 asynchronous isochronous IN source in the same active configuration and audio function. Prefer a declared IN link, then an IN endpoint marked implicit-feedback data. Plain async data IN requires the same resolved sample-clock route and the adjacent-interface/same-alt pairing used as evidence by ALSA, or a device quirk with equivalent evidence. An unqualified pair of async endpoints on a device is insufficient.
3. Resolve the IN and OUT terminals within their AudioControl interface and compare the actual source and sample-clock route. Reuse the strict terminal resolver, including actual selected pins. An assumed source, fallback-first source, or a multiplier with an unresolved ratio supplies insufficient evidence. Start with equal verified sample-clock cadence and equal IN/OUT service intervals. A shared master clock alone allows different sample-clock rates. Where needed, verify the active rate through existing rate controls. UAC1 or vendor-specific implicit pairings with sparse topology require a documented exact-device mapping and a compatible rate/control path.
4. Require usable whole-frame IN geometry and an effective OUT wire rate equal to the IN rate. The IN format and width may differ from OUT. Start with a known fixed-stride IN audio transport such as Type I PCM. Exclude padded or header-bearing IN formats unless the parser can validate and account for their overhead. A same-interface pair must coexist in the very same alternate. Reject a pair that needs two active alternates on one interface, zero/invalid intervals, or insufficient endpoint capacity. DoP can use the same engine where the IN rate matches the DoP carrier; native DSD needs a proven mapping to its actual wire frame rate.
5. If several alternates of the same proven IN pipe can satisfy the same rate and cadence, prefer the matching alt number, then the smallest valid bus reservation, then alt number. If equally plausible distinct sources remain, refuse with an ambiguity reason. Apply the current OUT format ranking to viable candidates, with feedback-paced candidates ahead of opted-in nominal async candidates for the same request.
6. If an async sink has no valid pairing, use the existing unsupported/fallback route. A known source that could not be claimed uses the existing typed claim failure if every viable route needs it. An opt-in nominal candidate is eligible only under the existing async policy and the declared-link safety rule. Reevaluate all these rules for the effective rate after negotiation, including rate substitution if already permitted by the request.

Separate structural capability from tested availability. A descriptor can show a source relationship before a rate is known. Only report a committed implicit source on `StreamFormat` after claim, rate and compatibility checks pass. Store its full identity on the native negotiated format, including playback endpoint and effective wire rate, since two plans can share otherwise identical format fields. Stream open must verify that identity or return the existing renegotiation error.

### 4.2 Android ownership and alt settings

Keep Kotlin's ownership of Android claims and the existing wrapped FD. Add a read-only native preflight for the active configuration that shares the Rust descriptor/topology scan. Invoke it from `UsbDac.open` after the base claims and before final native registration. It returns the configuration ID and capture-only interface IDs that satisfy structural pairing for one or more plausible async OUT alternates. This step does not set sample rates, change alternates or read audio. Claim each optional source through the existing `UsbDeviceConnection`, record actual successes plus unavailable source IDs, and register the full plan. A capture claim failure shouldn't discard usable explicit or synchronous alternates. Capture-only interfaces outside the plan remain with Android. If feedback is disabled, skip the preflight and optional claims. Android supplies an FD for native USB access through `UsbDeviceConnection`. [Android UsbDeviceConnection](https://developer.android.com/reference/android/hardware/usb/UsbDeviceConnection)

In Rust, retain strict equality for the required base claim set. Verify the optional set is a subset of the recomputed structural allowlist and contains no duplicates. Recheck configuration identity across preflight and registration. Rust embedders supplying preclaimed FDs use the same structural/actual-claim policy. For Android, retain successfully acquired optional interfaces for the life of the DAC session, so renegotiation has predictable claim semantics. Document that Android's capture on those interfaces is unavailable while held.

On stream open keep both streaming interfaces at alt 0 during shared UAC2 clock programming. Apply the negotiated IN and OUT alternates once each, IN first for separate interfaces, then verify the clock and start the IN pool. A same-alt pair needs one activation and one reset. Track every alt successfully activated in an owning guard. On a failure, reset the active list in reverse order after I/O has stopped. Include errors before worker spawn, thread creation failure, partial submit and unwind. Keep AC claims, volume hand-back and release/rebind under the existing session lifetime.

The IN endpoint delivers audio data at the USB layer. Read only transfer metadata for pacing. Discard the payload in internal buffers, without decoding, exporting, logging, storing or adding a recording API. Report activation and the capture interface identity in troubleshooting diagnostics.

### 4.3 Transfer model and packet counts

Reuse `IsoQueueGeometry`. Match IN and OUT service intervals and packets per transfer. Preallocate an IN transfer pool using the configured queue depth, with each request sized for the IN endpoint's capacity. Preallocate the pattern FIFO for `2 × out_slots` complete patterns and one pending entry per IN slot for reordering. Each pattern contains an IN submission sequence, exactly one frame count per service interval and a sum for diagnostics. Check allocation and index arithmetic, including the product of packets, capacity and slots.

The USB worker remains the only event pump and submitter. Callbacks publish completion status for the owned slot and return. The worker processes IN completions in submission order using their sequence, not slot index or completion wall time. A completion waiting for an earlier sequence retains its place in the bounded reorder storage. OUT completions release slots to the ready pool. The worker may submit from the ready pool only when the head pattern is available. Check slot ownership on every transition so a submitted slot can become ready exactly once.

For a completed IN transfer, validate its recorded packet count against the immutable geometry. For every packet, require successful packet status, `actual_length` within request and descriptor capacity, nonzero frame stride and a whole number of frames. Convert with:

```text
in_stride   = in_channels * in_subslot_bytes
out_stride  = out_channels * out_subslot_bytes
frames      = actual_length / in_stride     # require actual_length % in_stride == 0
out_bytes   = frames * out_stride          # checked multiplication and OUT capacity check
```

Pass the entire validated OUT size vector into `prepare_iso_transfer_payload` or its caller **before** popping or encoding samples. Apply the existing OUT frame accounting, native DSD/DoP encoding, marker phase, volume, payload audit, flush epochs and delivered-frame accounting. Keep byte-capacity and frame-alignment guards at the payload boundary. Make explicit and nominal pacing produce vectors through the same boundary. Retire each consumed pattern once and log separate counters for measured IN frames, scheduled frames, and delivered OUT frames. Compare converted **frame counts**, since byte totals can legitimately differ.

Use effective descriptor capacity per service interval. For USB 2.0 HS, multiply the lower 11-bit payload by one plus the additional transaction count. Reject reserved encodings. For SuperSpeed, use the companion descriptor's `wBytesPerInterval` when enabling implicit feedback at that speed. Keep initial implicit admission limited to validated speed/capacity combinations. [USB 2.0 §9.6.6](https://www.usb.org/document-library/usb-20-specification), [USB-IF USB 3.2 specification library](https://www.usb.org/documents?search=USB+3.2), [libusb ISO packet descriptors](https://libusb.sourceforge.io/api-1.0/group__libusb__asyncio.html)

### 4.4 Priming, steady state and recovery

```mermaid
flowchart LR
    IN[IN ISO slots] --> C[Reap in submit order]
    C --> V[Validate and count frames]
    V --> F[Bounded pattern FIFO]
    O[Ready OUT slots] --> P[Pair slot and pattern]
    F --> P
    P --> E[Prepare and encode OUT payload]
    E --> U[Submit playback]
    U --> O
```

- Wait for the existing producer prime threshold before scheduling IN or starting the feedback deadline. For implicit mode, start IN and collect consecutive valid patterns for the configured OUT queue depth. Keep reaping IN while initially submitting OUT. OUT starts only once the paired patterns are available. This trades roughly one configured bus queue of startup time for an initial full OUT queue. Record actual warm-up latency.
- During warm-up an all-empty IN transfer may indicate that the source has yet to start. Reset the consecutive-valid prime count and continue within a bounded startup budget. Initial proposal is `max(500 ms, 4 × transfer_duration)`. Runtime IN packets with zero measured frames are a gap for normal UAC PCM rates at the admitted intervals. Genuine sub-frame-capable transports need an explicit capability and a packetization policy.
- During playback a ready OUT slot may wait for new IN data while other OUT slots are still queued. Empty FIFO in isolation is normal. Bound a wait by available queued OUT coverage and raise a feedback fault on an observed empty bus queue, an expired wait budget, or FIFO overflow. Compute a conservative wait budget from submitted packet intervals and elapsed time since queueing, with a one-service-interval guard. This is a userspace estimate. Treat a hardware trace as the authority on actual bus starvation. Keep startup and running requests responsive to stop and detach even when no OUT slots are active.
- A malformed steady-state pattern becomes an ordered gap at its exact sequence. When it reaches the head, stop the feedback-paced stream before using directionally unknown lengths. Never skip a position in the pattern or reuse an old batch. Distinguish feedback discontinuity from playback PCM-ring underrun and from actual lost OUT frames. Treat known detach as device loss and ordinary stop as cancellation. A fixture that requires a bounded concealment policy must justify it separately with packet-level evidence.
- Require valid IN throughput before asserting lock. Use a rolling or consecutive complete service-time window of at least 100 ms and qualify the average against the negotiated rate with the existing ±2% starting limit plus one frame of quantization allowance per window. Base elapsed service time on packet count and descriptor cadence. Clear lock when a running discontinuity invalidates it. Treat two consecutive out-of-band windows as a stream failure. A single packet can legitimately differ from the average by a frame. Use packet bounds for immediate safety and the window for rate plausibility.
- Keep feedback running during pause, flush and drain. Pause and refill silence use the current fresh patterns. Flush cancels only old-epoch OUT payloads, services IN while retiring those cancellations, and reuses the newly ready slots with fresh patterns. The IN completion queue must remain bounded even if a flush outlasts available USB coverage. On that path emit a feedback fault and close cleanly. Never count canceled music as played or replay canceled patterns. Clear all queued patterns and rate history on stop, alt change, detach or restart.

The loss response deliberately changes the reference's underrun recovery. Reusing the newest timing pattern could work briefly, but the timeout policy and byte counts alone cannot recover the missed service intervals or prove the DAC stayed locked. A typed failure lets the application retry direct output or use its ordinary selection policy.

## 5. Explicit feedback hardening

### 5.1 Selection, normalization and capacity

Reuse `select_explicit_feedback_endpoint` for ISO IN and retain existing interrupt and three-byte HS compatibility where a current descriptor or regression case supports it. For UAC1 use the linked IN endpoint and respect `bRefresh` as the expected update cadence when valid. For UAC2 prefer a single eligible feedback-usage sibling in the selected alternate. For the handover's mislabelled UAC1 3/4-byte case, accept a unique second ISO IN sibling only when it is unlinked, matches a verified device rule, and lacks credible audio data framing. Full-speed interrupt `bInterval` is linear. ISO and high-speed interrupt interval rules are exponential. Use polling cadence and expected fresh-report cadence for scheduling and deadlines, with the bus timebase used only for rate decoding. [UAC1 §4.6.2](https://www.usb.org/sites/default/files/audio10.pdf), [USB 2.0 §9.6.6](https://www.usb.org/document-library/usb-20-specification)

Read exactly the report length from its ISO packet descriptor, using the offset determined by the requested packet lengths. Scan batched polls in wire order and apply the newest **valid** report. Invalid newer packets must leave an earlier valid report usable. Eliminate the current tail-slice truncation of oversize reports. Classify successful zero-length packets as empty polls, and separately count malformed sizes, packet status failures and rate rejections.

Decode little-endian three-byte Q10.14 as `raw << 2` or exact four-byte Q16.16. Standard high-speed reports have zero top four bits. Reject reserved bits in standards mode. A demonstrated compatibility path may mask them as ALSA does. Keep the existing known high-speed Q10.14 test behavior as a compatibility case where the report geometry and nominal-rate check identify it. Use an explicit rate-scale rule for devices sending frames per OUT service interval, including a test for the Linux gadget with a non-unit interval. Avoid auto-shifting arbitrary inputs to nominal. For an unresolved bus speed, require unambiguous rate units and service timing from the available speed sources or refuse feedback lock with a reason.

```text
usb_base_us = 1_000 for FS, 125 for HS
frames_per_out_service_q16 = feedback_q16 * (out_service_us / usb_base_us)
max_out_frames = effective_out_packet_bytes / out_stride
accept if the rate passes the nominal window and ceil(frames_per_out_service) <= max_out_frames
```

Convert once at report intake, then preserve fractional phase across reports. Use the existing nominal rational accumulator before lock. Keep the current 0.2 EWMA for accepted explicit updates initially to preserve the established path. Evaluate its response against the measured device cadence and OUT queue lead time. For a ±1000 ppm step, roughly 14 applied updates give 95% of the change with this coefficient. Use one update after detection plus bus queue lead time only as the response target if later measurements justify direct application of the new rate without smoothing. Frame budgets are based on actual wire frames, including DoP carrier and native DSD packing.

### 5.2 Streaming and loss of feedback

Retain the existing nonblocking, batched explicit IN pool on the USB worker. Start polling by the time OUT first primes. Allow the existing bounded nominal warm-up because some DACs wait for OUT data before giving feedback. Test one slot with the current polling window first, then use two prequeued batch slots if there are measured scheduling gaps. Size the polling horizon against the device cadence, bus queue and processing budget. Eight one-packet slots and a separate thread remain a tuning option if traces show the worker model cannot keep the pipe serviced.

Track startup from the first active transfers. Propose a stale warning at `max(500 ms, 3 × expected_update_period)`, then a terminal deadline at `max(1 s, 6 × expected_update_period)`. The same deadline bounds time without a first good report. Distinguish no update, transient timeout and submit failure. Retry transient timeouts or submission errors with bounded backoff while the other endpoint continues. Hold the last good rate through the warning interval and clear feedback lock there. On terminal failure stop both pipes and emit a typed failure. Cancellation on commanded stop is normal. On `NO_DEVICE` take the device-loss path promptly. Allocation or first submit failure on a selected explicit route fails stream start with the relevant USB error. The live mode must not silently turn nominal while reporting explicit pacing.

## 6. Public contract and cleanup

- Add Rust `Pacing::ImplicitFeedback` and Kotlin `Pacing.ImplicitFeedback` carrying source interface, alt and endpoint. Wire value `implicit_feedback`. Preserve `explicit_feedback`, `has_explicit_feedback` and the explicit-only `feedback_endpoint` field. Publish the implicit source in an additive field and keep legacy JSON fields available. Kotlin clients with exhaustive `when` on the sealed pacing type need a new branch. If adding a public config constructor field, append it, preserve existing JVM constructor overloads where possible, and document affected precompiled Kotlin call sites and exhaustive Rust struct literals.
- Prefer a single `disable_feedback` / `disableFeedback` session setting defaulting to false. Disabling prevents both feedback modes from running. Use existing opt-in to permit nominal async playback where the descriptor is otherwise usable. Disabled and unsynchronized remain observable. Retain exact-device opt-outs and startup/format overrides in the existing quirk layer, each with a descriptor snapshot or reproducible evidence and a reason. Omit the reference's vendor whitelist.
- Live feedback status has priming, locked and stale states, with terminal failure carried through the existing `StreamFailed` event path. Make `feedback_active` represent valid active pacing for either mode. Add a feedback-unlocked bit-perfect blocker and keep the existing lost-audio latch, verified clock, format, software gain and payload requirements. The negotiated pacing label states which mechanism the stream uses even during prime or cleanup. Review UI text and OutputSelector's guarantee so a successfully negotiated route never implies a live verified stream.
- Keep the stable codes for unsupported implicit pairing, claim failure and detach. Report runtime feedback faults as `Error::Transfer` / `DacErrorCode.TRANSFER` through `StreamFailed`, with the mode, source and failure reason in diagnostics. A claim succeeded at session open can still fail to activate at stream open. Preserve the actual activation error and reset any other alternate already selected.
- Publish accepted, empty, rejected and timed-out report counts, last valid age, effective feedback rate and reason for lock changes. For implicit add FIFO current/high-water depth, wait count, actual empty-bus and overrun counts, IN/out-of-order/invalid packet counts and measured-versus-scheduled frame totals. Update by interval or state transition. Replace the reference's callback-count log cadence with the existing periodic stats pattern and bounded fault logs.
- Stop and teardown share one path. Stop new submissions, cancel both IN and OUT pools, pump events until all submitted slots are returned, then release buffers, reset alternates, return the handle to idle or close it, and release Kotlin claims on session close. Cancel returns asynchronously. Preserve transfer storage, context, handle and FD ownership together if a drain stalls. A bounded public stop can leave an owner draining in the background and block new ownership until it retires. Never hand an undrained handle or alternate to a new session. Use the same invariant on detach and panic. [libusb asynchronous cancellation](https://libusb.sourceforge.io/api-1.0/group__libusb__asyncio.html)

## 7. Implementation batches

### Batch 1 — implicit feedback from discovery to playback

1. Add the descriptor inventory, strict pairing resolver and capture source identity. Feed the result into capability discovery, negotiation, stream-open revalidation and endpoint audit. Reuse the existing format and clock data structures.
2. Wire the Android preflight and optional claim results through the existing JNI/native open. Add multi-interface alt ownership and consolidate cancel/drain handling so the worker can release both pools safely.
3. Add implicit IN slots, ordered completion handling, preallocated pattern FIFO and ready OUT scheduling to the worker. The loop must keep receiving IN completions while OUT is starting or has no ready payload. Bound event-pump waits by the next relevant deadline rather than relying on the existing 50 ms event wait. Include flush and pause in the same change.
4. Add implicit pacing diagnostics, live lock and typed failures across Rust, JNI and Kotlin. Refresh `README.md`, `docs/API.md` and the SDK transport, controls, automatic-output and troubleshooting descriptions of implicit feedback. Use the actual setup path in the sample when presenting availability.
5. Validate the end-to-end implicit path as a batch. Reuse existing explicit tests and Android smoke evidence where still applicable. Re-run explicit playback and a synchronous/adaptive control because the worker and payload boundary change.

### Batch 2 — explicit compatibility and failure handling

1. Tighten pipe discovery, transfer report extraction, interval handling and rate/capacity validation. Reuse the original scheduler's nominal accumulator and explicit smoothing. Cover sparse reports and the Linux gadget's non-unit OUT interval.
2. Apply the live feedback lock, fault classification and safe stop path to explicit streams. Keep post-priming stall and unsupported async fallback behavior explicit in the public contract.

For a healthy implicit run after priming, the release criterion is zero feedback overruns, zero feedback deadline faults and zero unexplained lost OUT frames. At a matched checkpoint, cumulative valid IN frames minus scheduled OUT frames equals the frames still pending in the capture-to-playback queue, with intentional warm-up discards separately accounted for. Submitted minus delivered OUT frames must reconcile with in-flight and explicitly canceled or lost frames. The difference must stay bounded by the configured queues with no trend over the 24-hour run. Audible playback complements packet and byte accounting. For explicit step tests, record report bytes, accepted-report cadence, queue lead and measured convergence separately. The packet trace and report history should account for the observed response.

Use Android debug logs and packet metadata in both cases. Capture a representative USB trace with an analyzer or supported usbmon path when available. Keep capture-payload logging disabled. Preserve evidence from a failed acceptance run before changing the next batch.

## 9. Evidence still needed for release

- A real marked implicit device on an Android host, plus a trace-supported exact-device fallback to establish the compatibility path. The current repository's documented phone/DAC playback and the reference suite do not provide this evidence.
- The initial IN-first queue depth, feedback deadlines and high-rate queue behavior measured on at least the oldest supported Android target used for acceptance. They are design defaults subject to the observed completion and submission gaps.
- Descriptor/control and packet evidence before enabling unlike service intervals, native-DSD implicit timing, SuperSpeed implicit admission, or a playback-first quirk. The equal-cadence, whole-frame queue is deliberately independent of format-specific conversions, leaving those cases a compatible extension point.
- Confirmation that optional capture claim/rebind and delayed cancel behave as designed on Android usbfs. Linux kernel URBs and libusb userspace slots have different ownership and scheduling interfaces.

Implementation source should be independently written against this repository's MIT code and the documented behavior. The local reference identifies the algorithms and examples, but its package currently declares no license. The Linux files provide interoperability evidence and test expectations. Keep their GPL source out of the MIT implementation and retain the existing third-party notices.
